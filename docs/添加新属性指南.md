# 添加新属性指南

给豆子 / 磨豆机 / 冲煮记录加属性时，**先判断它属于哪一类**。
走错路的代价不是「多写几行」，而是查询全面退化或数据迁移。

---

## 0. 先做判断

| 这个属性需要… | 走哪条路 | 代价 |
|---|---|---|
| 只记录、只展示（购买渠道、海拔、序列号） | **扩展属性** | 加一行定义，**不改表、不迁移、不改表单** |
| 被筛选 / 排序 / 统计（按烘焙商筛豆子、按粉量排序） | **晋升为一等列** | 改 6 个地方 + 迁移，见 §2 |
| 是核心参数的同类项（例如新增「闷蒸时间」） | **晋升为一等列** | 同上 |
| 不确定 | 先用扩展属性 | 将来真需要查询时再晋升（§3 有步骤） |

**判断标准就一句：这个字段会不会出现在 `WHERE` / `ORDER BY` / 聚合里？**

会 → 一等列。不会 → 扩展属性。

为什么不能一律用 key-value：一旦要按 key 过滤，就得
「全表扫描 + 逐行 JSON 解析」，`adjustStock`、按豆筛选、调磨对比
这些都会被拖慢，而且没法建索引、没法加外键约束。

## 1. 加一个扩展属性（推荐路径）

### 1.1 加内置定义

打开 `lib/domain/extra_attributes.dart`，往对应列表加一行：

```dart
// 咖啡豆
static const List<ExtraAttributeDefinition> bean = <ExtraAttributeDefinition>[
  // ...已有项
  ExtraAttributeDefinition(
    key: 'roaster',                    // 稳定标识：只用字母数字，别改
    type: ExtraValueType.text,         // 决定表单用什么控件
    label: '烘焙商',                    // 界面显示名
    hint: '例如：M2M、啟程拓殖',         // 可选的输入提示
    sortOrder: 10,                     // 数值小的排前面
  ),
];
```

**就这一步。** 之后：

- 表单的「更多信息」区块会自动出现该字段（`ExtraAttributesEditor` 按注册表渲染）
- 详情页会自动展示已填的值（`ExtraAttributesSummary`）
- 导出会自动带上（扩展属性整份导出）

### 1.2 可用的值类型

| `ExtraValueType` | 表单控件 | 说明 |
|---|---|---|
| `text` | 单行输入 | 默认 |
| `number` | 小数键盘 | 存 `double` |
| `integer` | 数字键盘 | 存 `int` |
| `boolean` | 开关 | 存 `bool` |
| `date` | 日期选择器 | 存 ISO8601 字符串 |
| `tags` | 输入 + 「、」分隔 | 存 `List<String>` |

### 1.3 用户自建属性

用户可以在详情页自己加 key（`isBuiltin = false`）。这类属性同样会被
展示与导出，只是不保证稳定——所以**内置定义只放真正常见、需要统一语义的属性**。

### 1.4 命名与兼容约定

- `key` 只用 `^[a-zA-Z][a-zA-Z0-9]*$`，有测试强制校验
- **`key` 一旦发布就不要改**：数据库里存的是它，改了就读不到旧数据
- `ExtraOwnerType.bean.storageKey` 同理（存的是 `'bean'` / `'grinder'`）
- 未知的 `valueType` 会回落到 `text`，所以新增类型不会让旧数据渲染崩溃
- 有测试守住「同一 owner 内 key 不重复」与「key 命名合法」

## 2. 晋升为一等列（需要改 6 个地方）

以「给豆子加 `roaster`（烘焙商），并要能按它筛选」为例。

### 2.1 表定义

`lib/data/database.dart` 的 `CoffeeBeans` 加列：

```dart
TextColumn get roaster => text().nullable()();
```

需要按它筛选时再加索引：

```dart
@DataClassName('CoffeeBeanRow')
@TableIndex(name: 'idx_coffee_beans_roaster', columns: {#roaster})
class CoffeeBeans extends Table { ... }
```

### 2.2 递增 schemaVersion + 写迁移

```dart
int get schemaVersion => <现值 + 1>;   // 现值以 lib/data/database.dart 为准，别照抄数字
```

> ⚠️ **禁止把版本号写小。** 写小比忘记递增危险得多：drift 会认为发生了升级，
> 把 `PRAGMA user_version` **静默降回**旧值（不报错），等修好后重新发版时 `from` 变成那个旧值，
> 迁移段会对着**已存在**的列再跑一次 `addColumn` → `duplicate column name` →
> **数据库打不开、App 起不来**（用户数据大概率还在盘上，但进不去）。
>
> ⚠️ **改类型 / 改主键只能重建表，但重建被外键引用的表会级联删数据。**
> `coffee_beans` 被 `bean_batches` / `brew_log_beans` / `brew_logs` 引用着，删父表会把刚搬好的
> 批次与用量行一起删掉。这条路径本项目**没有验证过** → **停下报 `BLOCKED` 并问人**，
> 不要在生产迁移里做第一次尝试（完整裁决见
> [`agent-teams/AgentTeams-开发手册.md`](agent-teams/AgentTeams-开发手册.md) §7.3 第 6 条）。
>
> **加列 / 删列 / 改枚举的值 / 建新表**，一律用 `addColumn` / `dropColumn` / `createTable`
> + 改写值，**不重建已有表**（v4 → v5 → v6 → v7 全是加列 / 建新表 / 改写值
> —— **没有一次重建已有表**；删列只出现在 v1 → v4 那次搬迁里）。

**关键：`onUpgrade` 是逐列迁移，不能再用删表重建。**
（v1 → v4 的那次搬迁就是这么写的，见 `lib/data/database.dart` 的 `_upgradeToV4`，
其中也解释了「为什么用 `dropColumn` 而不是 `alterTable` 重建表」。）
可加列时用 `m.addColumn`：

```dart
onUpgrade: (m, from, to) async {
  // ⚠️ 这里的 5 只是示意，**必须与 §2.2 里 schemaVersion 的「本次新值」一致**。
  // 写死一个过期数字的后果：现有用户（from = 现值）走的是"不需要迁移"的分支，
  // addColumn 根本不执行 → 物理表没有这一列，而 Dart 侧有 → 任何读这张表的查询
  // 直接 `no such column`。（`test/data/schema_snapshot_test.dart` 的 _fixtures 循环
  // 会从每个历史版本各升一遍，能抓到它 —— 但别指望 CI 替你发现。）
  if (from < 5) {
    await m.addColumn(coffeeBeans, coffeeBeans.roaster);
  }
}
```

（新增可空列是安全的；改类型、改主键见上面的 ⚠️ —— 那是另一类操作，且未验证。）

⚠️ 别忘了**给这次迁移补一个「旧库升上来」的测试**：
`test/data/migration_v1_to_v4_test.dart` 里造旧库、跑迁移、断言数据与新库结构一致，
照那个模式加一份即可（旧库的建表语句从旧提交的 `sqlite_master` dump，不要手抄）。

### 2.3 实体

`lib/domain/entities.dart` 的 `CoffeeBean`：加字段 + `copyWith` 参数 +
`toJson` / `fromJson` + `==` / `hashCode`。

### 2.4 映射

`lib/data/mappers.dart` 的 `CoffeeBeanRowMapper.toEntity` 与
`CoffeeBeanCompanionMapper.toCompanion` 各加一行。

### 2.5 表单与展示

- `lib/features/beans/bean_form_page.dart` 加输入控件
- `lib/features/beans/beans_page.dart` 卡片上决定是否展示

### 2.6 测试

- `test/data/design_decisions_test.dart`：加列的读写往返
- 若参与筛选：加查询测试
- 若加了索引：`EXPLAIN QUERY PLAN` 断言走索引

### 2.7 迁移已有数据（可选）

如果这个属性以前是扩展属性，想把它搬成列：

```dart
// onUpgrade 里
final rows = await customSelect(
  "SELECT owner_id, value FROM extra_attributes "
  "WHERE owner_type = 'bean' AND key = 'roaster'",
).get();
for (final row in rows) {
  await (update(coffeeBeans)
        ..where((t) => t.id.equals(row.read<int>('owner_id'))))
      .write(CoffeeBeansCompanion(
    roaster: Value(row.read<String?>('value')),
  ));
}
```

## 3. 从扩展属性晋升的时机

先用扩展属性，等到确实需要查询时再晋升。信号：

- 界面上出现了「按 X 筛选 / 排序」
- 统计里要按 X 分组
- 导出后用户抱怨「没法在 Excel 里按 X 排序」

不要提前晋升：每多一个一等列，就多一次迁移、多一处表单、
多一组测试要维护。

## 4. 冲煮记录同理

冲煮记录的「专业字段」现在都是平铺的列（`tds`、`waterPpm` …）。
如果以后要加**只记录**的实验性参数（例如「滤纸品牌」「搅拌次数」），
用同样的扩展属性机制即可——只需给 `ExtraOwnerType` 加一个枚举值：

```dart
enum ExtraOwnerType {
  bean('bean', '咖啡豆'),
  grinder('grinder', '磨豆机'),
  brewLog('brewLog', '冲煮记录'),   // 新增
}
```

再在 `ExtraAttributeRegistry.of()` 里加对应分支与定义列表。
表结构、仓库、编辑器都不用改。

## 5. 加一个枚举值（不用迁移）

`lib/domain/enums.dart` 里每个枚举都区分**存储全集**（`values`）与
**表单可选子集**（`selectable`）：

```dart
enum BrewMethod {
  pourOver('手冲'),
  mokaPot('摩卡壶'),
  // 预留值：已在存储全集里，只是暂时不在选择器里出现
  frenchPress('法压壶'),
  // ...
  ;

  static const List<BrewMethod> selectable = [pourOver, mokaPot];
}
```

- **开放一个预留值** → 把它移进 `selectable`。不动表、不迁移。
- **加一个全新值** → 往 `values` 加一项，再决定是否放进 `selectable`。
  因为列是 `TEXT`，加值本身不需要迁移。
- **旧版本读到新值**（前向兼容）→ 不会崩，见 §5.1。

### 5.1 未知枚举值必须能优雅降级（已实现）

**这里踩过一个会真崩的坑**，值得单独说：

Drift 的 `textEnum<T>()` 内部用 `values.byName(...)` 解码，
**遇到不认识的字符串会抛 `ArgumentError`**。也就是说：
新版本加了「法压壶」，旧版本读到那条记录会**直接崩溃**。

而且修的时候还踩了第二层：写成 `textEnum<T>().map(自定义转换器)`
**没用**——`textEnum<T>()` 内部已经挂了一个 `EnumNameConverter`，
外面再 `.map()` 只是又包一层，**内层那个抛异常的转换器仍然先执行**。

正确写法是**彻底不用 `textEnum`**，用裸 `text()` 接自己的转换器：

```dart
// ✅ 认不出就回退，不崩
TextColumn get process => text()
    .map(const TolerantEnumConverter<ProcessMethod>(ProcessMethod.values))
    .nullable()();

// ❌ 这样写内层仍会抛异常
TextColumn get process => textEnum<ProcessMethod>()
    .map(const TolerantEnumConverter<ProcessMethod>(ProcessMethod.values))
    .nullable()();
```

代价：非空枚举列（`brew_logs.method`、`grinders.scaleUnit`）在 Dart 侧
变成可空，映射层要回退默认值（已经在 `mappers.dart` 里做了）。
这个代价是值得的——**崩一次比多一行 `??` 严重得多**。

有测试守住这一点：直接往库里写一个不存在的枚举值，
断言读取不抛异常且回退为 null。

## 6. 加一类可扩展对象

想让某类实体（例如「配方」）也支持扩展属性，已经做好了，不用改表：

```dart
enum ExtraOwnerType {
  bean('bean', '咖啡豆'),
  grinder('grinder', '磨豆机'),
  brewLog('brewLog', '冲煮记录'),
  batch('batch', '豆子批次'),
  recipe('recipe', '配方'),
  // 新增就加一行
}
```

再在 `ExtraAttributeRegistry.of()` 里补一个分支与定义列表。
仓库、编辑器、导出都不用动——**漏了分支编译不过**，由编译器兜底。

需要便捷入口的话，在 `ExtraAttributeRepository` 里加三行：

```dart
Future<List<ExtraAttribute>> getForRecipe(int id) =>
    getAll(ExtraOwnerType.recipe, id);
```

## 7. 检查清单

加扩展属性：

- [ ] `key` 符合 `^[a-zA-Z][a-zA-Z0-9]*$` 且不与已有重复
- [ ] 选了合适的 `ExtraValueType`
- [ ] 给了 `label` 与 `hint`
- [ ] 跑了 `flutter test test/data/extra_attributes_test.dart`

加枚举值：

- [ ] 往 `values` 加项（列是 TEXT，不需要迁移）
- [ ] 需要出现在选择器里就加进 `selectable`
- [ ] **不要**改用 `textEnum()`——会破坏未知值降级

加可扩展对象类型：

- [ ] `ExtraOwnerType` 加枚举值
- [ ] `ExtraAttributeRegistry.of()` 补分支（漏了编译不过）
- [ ] 需要的话在仓库加便捷方法

晋升为一等列：

- [ ] 表定义加了列（需要筛选时加索引）
- [ ] `schemaVersion` 递增（**只往大写**，见 §2.2 的 ⚠️）
- [ ] `onUpgrade` 写了**逐列迁移**（不是删表重建）
- [ ] 跑了 `dart run build_runner build --delete-conflicting-outputs` 重新生成 `database.g.dart`
- [ ] 跑 `dart run drift_dev schema dump lib/data/database.dart test/drift/schemas`
      和 `dart run drift_dev schema generate test/drift/schemas test/drift/generated`
      更新冻结快照（忘了跑，`test/data/schema_snapshot_test.dart` 会红并点名那一列）
- [ ] 为新版本在 `test/data/schema_snapshot_test.dart` 的 `_fixtures` 里**补了一份「旧库升上来」的夹具**
      （复用上一版的写入函数，只补这次新增的东西；不补，守门用例会直接点名要你补）
- [ ] 真机**覆盖安装**验证：旧数据原样在、无 drift / SQLite 报错（**通过之前不对外发版**）
- [ ] 实体 + `copyWith` + JSON + `==`/`hashCode`
- [ ] 两个方向的映射
- [ ] 表单与展示
- [ ] 测试（读写往返 + 筛选/索引）
