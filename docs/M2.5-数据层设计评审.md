## 1. 当前结构（v3）

```text
coffee_beans（豆子：一款豆子的身份）
  id, name, origin, farm, process,
  flavorTags, isFavorite, photoPath, notes, createdAt, updatedAt
        │ 1:N（级联删除）
        ▼
bean_batches（批次：每一次购买）
  id, beanId, roastDate, roastLevel,
  remainingGrams, initialGrams, price, notes, createdAt, updatedAt

brew_logs（冲煮记录）
  id, beanId(主豆冗余), grinderId, recipeId, method,
  grindSetting, grindClicks, doseGrams(总粉量), waterGrams, ratio,
  waterTemp, totalTimeSeconds, dripper, rating, flavorTags, notes, photoPath,
  brewedAt, isBest,
  tds, extractionYield, waterPpm, ambientTemp, ambientHumidity,
  beanTemp, pressure, pourStages,
  beanRoastDate, beanRoastLevel,          ← 烘焙快照
  heatLevel, yieldGrams, preheatUpperChamber, createdAt, updatedAt
        │ 1:N（级联删除）
        ▼
brew_log_beans（这条记录用了哪几支豆子）
  id(自增主键), brewLogId, beanId, batchId,
  beanNameSnapshot, roastDateSnapshot, doseGrams, position
```

索引（v3 新增）：

```sql
idx_bean_batches_bean_id            ON bean_batches (bean_id)
idx_brew_logs_brewed_at             ON brew_logs (brewed_at)
idx_brew_log_beans_brew_log_id      ON brew_log_beans (brew_log_id)
idx_brew_log_beans_bean_id          ON brew_log_beans (bean_id)
```

外键删除行为：

| 关系 | 行为 | 理由 |
|---|---|---|
| 豆子 → 批次 | `CASCADE` | 批次属于豆子，没有独立意义 |
| 豆子 → brew_logs.beanId | `SET NULL` | 记录要保留 |
| 磨豆机 → brew_logs.grinderId | `SET NULL` | 同上 |
| 记录 → brew_log_beans | `CASCADE` | 用量属于记录 |
| 豆子 → brew_log_beans.beanId | `SET NULL` | **用量行要保留**，靠快照名显示 |
| 批次 → brew_log_beans.batchId | `SET NULL` | 批次没了但用量仍要保留 |

## 2. 设计决策与理由

### 2.1 为什么把余量 / 烘焙日期移到批次

原设计里 `coffee_beans` 直接持有 `roastDate`、`remainingGrams`、`price`。
复购同一款豆子时只能**新建一支重复的豆子**，于是豆库里出现多个「耶加雪菲」，
按豆筛选与调磨对比都被割裂。

拆分后：豆子代表**身份**（不随购买变化），批次代表**这一袋**（每次购买都不同）。
复购 = 给已有豆子加一个批次。

### 2.2 多豆冲煮为什么用关联表而不是 JSON 字段

拼配需要「每支豆子各自的粉量」，且要能按豆筛选、能分别扣减余量。
JSON 字段无法建索引也无法做外键约束，所以用 `brew_log_beans` 关联表。

### 2.3 为什么 `brew_logs` 还保留 `beanId`

冗余字段。列表展示、按豆筛选、调磨对比都要「主豆」，每次都联
`brew_log_beans` 再取 position 最小的一支代价更高。
代价是必须保证它与用量表一致——由 `BrewLogRepository.save()` 统一写入来保证。

### 2.4 为什么记录里存烘焙快照

`beanRoastDate` / `beanRoastLevel` 与 `beanNameSnapshot` / `roastDateSnapshot`
随记录存一份。豆子或批次信息后来被改、甚至豆子被删除，
历史记录仍能还原「当时用的是什么豆」。

### 2.5 余量扣减的边界规则

全部集中在 `BeanRepository.adjustStock()` 的一个事务里：

- **下限 0**：扣多了扣到 0，并在返回值标 `clamped`
- **0.1g 归一**：写入前按十进制字符串归一，避免反复加减累积浮点误差
- **`applied` 用 `before - after` 反推**，不用传入的 delta——
  被裁剪时它才反映真实生效量
- **未指定批次时**自动挑：优先「有余量 + 烘焙日期最新」的，
  排序链是 `烘焙日期 → 创建时间 → id`；全用完了则挑任意一个，
  好让扣减能落到 0
- **指定批次已不存在时**会退回到自动挑选，并通过
  `fallbackFromBatchId` 明确告知，**不静默换扣**
- 编辑记录时**按差值补扣**，不重算历史；换豆则旧豆回补、新豆扣减
- 删除记录**不回补**（手册 §6.2）

> 排序链里 `id` 不是装饰：Drift 的 `dateTime()` 按 **Unix 秒** 存储，
> 同一秒内创建的两个批次 `createdAt` 会完全相同，只按它排序结果不确定。

## 3. 问题清单与处理结果

### ✅ 问题 1：外键缺索引 → 已修

新增 4 个索引（见 §1）。有测试用 `EXPLAIN QUERY PLAN` 断言
按豆查批次确实走了 `idx_bean_batches_bean_id`。

### ✅ 问题 2：删除豆子会破坏多豆记录的历史 → 已修

`brew_log_beans` 换成**自增主键**，`beanId` 改 `SET NULL`，
并新增 `beanNameSnapshot` / `roastDateSnapshot`。

为什么必须换主键：原来的复合主键 `(brewLogId, beanId)` 要求 `beanId` 非空，
所以只能级联删除整行；而且 `beanId` 置空后复合主键还会冲突。
换自增主键后，同一条记录的两支豆子都被删除也能各留一行。

测试覆盖：删一支 / 删两支 / 级联删记录。

### ✅ 问题 3：浮点误差 → 已按 0.1g 归一

`roundGrams()` 用 `double.parse(value.toStringAsFixed(1))`。

**这里踩过一个坑**：最初写成 `(value / 0.1).round() * 0.1`，看起来对，实际错——
`97 * 0.1` 得到的是 `9.700000000000001` 而不是 `9.7`（两个是不同的 double），
等于把误差又引回来了。走十进制字符串才能拿到 `9.7` 那个 double。
另外**必须先归一 `remaining` 再减**，否则 `roundGrams(before - delta)`
之后仍会残留二进制误差。

测试覆盖：30 × 0.1g 精确落到 7.0、100 × 0.1g 精确归零、回补保持精度。

### ✅ 问题 4：`beanId` 双重记账 → 保留 + 注释约束

性能值得。已在 `BrewLogRepository` 注明「只允许经 `save()` 写入」。

### ✅ 问题 5：烘焙快照 → 保留

历史可还原优先于消除冗余。有测试断言「批次烘焙日期之后被改，
历史记录的快照不变」。

### ✅ 问题 6：迁移策略 → 已落地为逐列迁移

原来的 `onUpgrade` 是 `deleteTable` + `createAll`（当时无用户数据）。
现在换成了**逐列迁移** `_upgradeToV4`（`lib/data/database.dart`）：
建新表 → 把烘焙/余量/价格搬成每个豆子的第一个批次 → 用 `brew_logs.bean_id`
回填用量行与烘焙快照 → 最后才改 `coffee_beans` 的形状。

配套 `test/data/migration_v1_to_v4_test.dart`：造一个真正的 v1 库（建表语句从
`e1f6946` 的 `sqlite_master` dump），跑迁移后断言数据没丢、且结构与全新建库**完全一致**。

> 顺带纠正一个记录错误：v2 / v3 从未存在过。`git log -L` 显示 `schemaVersion`
> 只变过一次（1 → 4），所以迁移只需要一条 v1 → v4 的路径。

### ✅ 问题 7：批次挑选隐式 → 已成显式

`AdjustStockResult.fallbackFromBatchId` + `SaveBrewLogResult.hasBatchFallback`
让 UI 能提示「原批次已不在，改扣了别的批次」。

### ✅ 问题 8：新增豆子强制首个批次 → 已定

UI 层按「豆子 + 首个批次」一起提交；数据层已支持
`addBeanWithBatch` 这类组合写入。
