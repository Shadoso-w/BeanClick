# 豆刻审查报告模板（三份 + 共同规矩）

> 用途：`rev-spec` / `rev-code` / `info-reviewer` 复制对应那一段，填完就是一份可直接交回 `lead` 的报告。
> 角色与写作用域见 [`AgentTeams-开发手册.md`](AgentTeams-开发手册.md) §3.2，
> 门禁顺序见 §5.1；推送前审核的完整判定口径见 [`../REVIEW-BEFORE-PUSH.md`](../REVIEW-BEFORE-PUSH.md)。
>
> 审查者**只写报告，不代改代码**：报告里的每条都必须带一个可执行动作，
> 由实现者或 `lead` 去落地。

---

## 0. 结论词表（唯一口径，不许自造）

**审查结论（三份报告各用一套）**

| 报告 | 三档结论 | 含义 |
|---|---|---|
| 规格符合性（`rev-spec`） | **通过** / **有条件通过** / **打回** | 需求点逐条有落点、无缺项 → 通过；有缺项但可控 → 有条件通过；缺项构成核心缺口 → 打回 |
| 代码质量（`rev-code`） | **通过** / **有条件通过** / **打回** | 无阻断项 → 通过；只剩建议项 → 有条件通过；有未修复的阻断项 → 打回 |
| 信息审核（`info-reviewer`） | **可推送** / **有条件通过** / **阻止** | `BLOCK=0` 且 WARN 逐条有结论 → 可推送；条件落地并复核后可推 → 有条件通过；有阻断项 → 阻止 |

**配合用到的其它词表**

| 词表 | 取值 |
|---|---|
| 门禁 | G0–G7，特区门 DG / MG / PG |
| 任务状态（写进 `PROGRESS.md` 时） | `todo` / `in_progress` / `spec_review` / `code_review` / `blocked` / `done` / `dropped` |
| subagent 返回四态 | `DONE` / `DONE_WITH_CONCERNS` / `NEEDS_CONTEXT` / `BLOCKED` |
| 严重度 | 阻断 BLOCK / 警告 WARN / 提示 INFO |
| 硬编码三档 | 合理 / 建议提取 / 必须外置 |

**禁止出现**：「基本没问题」「差不多完成」「应该没事」「大体上通过」。
结论只有上表的取值；说不清就写「证据不足」并把缺什么写出来。

## 1. 规格符合性审查报告（`rev-spec`）

> 输入：任务卡 ID + 需求点清单 + 设计稿（UI 类改动）。目的只有一个：
> **需求点有没有全部落地，且每一条都有测试**。不看代码风格（那是 `rev-code` 的事）。
> 顺序铁律：规格符合性没过，不得启动质量审查。

```markdown
# 规格符合性审查：<任务卡 ID>

结论：通过 / 有条件通过 / 打回
范围：<任务卡 ID> · <分支名> · <文件清单>
需求来源：<任务卡原文 / 设计稿路径（例 `docs/M2.10-研磨刻度设计稿.md`）>

## 需求点逐条对照

| # | 需求点（编号 + 原文摘要） | 落点文件 | 是否有实现 | 是否有测试 | 结论 |
|---|---|---|---|---|---|
| 1 | <需求点原文> | `<路径>:<行号>` | 是 / 否 / 部分 | 是（`<测试文件>:<用例名>`）/ 否 | 符合 / 不符合 |
| 2 | | | | | |

## 缺项清单

| # | 缺什么 | 影响 | 具体动作（改成什么 / 补哪个文件） |
|---|---|---|---|
| 1 | <例如：`mappers.dart` 少一处双向映射> | <运行时会怎样> | <补 `toJson` / `fromJson` 的哪一段> |

## 受影响却未更新的既有测试

| 既有测试文件 | 用例 | 为什么受影响 | 处理 |
|---|---|---|---|
| `test/<...>` | <用例名> | <断言哪一个旧行为> | 改断言 / 删除 / 新增替代用例 |

## 疑点与待确认

- <需求点本身有歧义的地方，附任务卡原文与设计稿对应段落；不要自行拍板>

## 结论理由

- 通过 / 有条件通过 / 打回 的具体依据（逐条对应上面的表）。
```

**填写要求**

- 「是否有实现」必须给**行号**，不许只写文件名。
- 「是否有测试」必须是**能复现该需求点的用例**；只覆盖相邻代码不算。
- 余量扣减 / 导出格式 / 统计计算这三类改动缺单元测试，直接判「不符合」，没有例外
  （[`CONTRIBUTING.md`](../../CONTRIBUTING.md)）。
- 打回时写清「回到哪一步」：通常是补实现或补测试后重审本卡，而不是开下一张卡。

## 2. 代码质量审查报告（`rev-code`）

> 输入：规格审查**已通过**的那一版实现。目的：找出真会出事的问题，
> 不做风格洁癖。每条都要能被实现者直接动手修。

```markdown
# 代码质量审查：<任务卡 ID>

结论：通过 / 有条件通过 / 打回
范围：<任务卡 ID> · <分支名> · <文件清单>
基准：`flutter analyze` <输出摘要> · 本卡测试 <命令 + 通过数 + 退出码>

## 阻断项（必须修完才能开下一张卡）

| # | 文件:行号 | 问题 | 为什么是阻断 | 具体改法 |
|---|---|---|---|---|
| 1 | `<路径>:<行号>` | <问题> | <违反哪条铁律 / 会造成什么> | <改成什么> |

## 建议项（不阻断，但要有结论）

| # | 文件:行号 | 问题 | 建议改法 | 采不采纳由 `lead` 决定 |
|---|---|---|---|---|
| 1 | `<路径>:<行号>` | | | |

## 已确认无问题项（逐项打勾，不许合并成一句）

- [ ] **lint / 静态检查**：`flutter analyze` → No issues found!（贴原始输出摘要）
- [ ] **命名**：表意优先于简短；类 / 方法 / 变量名与豆刻既有命名一致，无 `tmp` / `data2` 之类残留
- [ ] **注释约定**：中文注释可以，但**公共 API 用英文文档注释**（`CONTRIBUTING.md`）
- [ ] **测试压在真实风险点上**：
  - 余量扣减 —— 有单元测试，且断言的是**批次余量**，不只是 `doseGrams`
  - 导出格式 —— 有编码 + 落盘的普通 `test`，不是只测 widget 接线
  - 统计计算 —— 有单元测试，覆盖边界（空数据 / 单条 / 拼配）
- [ ] **依赖底线**：未引入任何广告 / 埋点 / 崩溃上报类依赖（`pubspec.yaml` 的 diff 已逐行看过）
- [ ] **写作用域**：改动文件没有越出任务卡声明的 scope；没有碰生成物 `database.g.dart` / 快照
- [ ] **未越权**：没有 `git add` / `commit` / `push` 痕迹，没有全量 `dart format .`

## 结论理由

- <依据上面各表；只剩建议项 → 有条件通过；有阻断项 → 打回>
```

**填写要求**

- 「已确认无问题项」每一项都要有**可核查的依据**（命令 + 输出摘要，或文件行号），
  只打勾不写依据等于没查。
- 风格偏好（换行、括号、私有命名习惯）不进阻断项；放进建议项并说明收益。
- 发现测试只覆盖 happy path、或断言的是实现细节而非行为时，算**建议项及以上**；
  若该测试是这门改动的唯一回归网，升级为阻断项。

## 3. 信息审核报告（`info-reviewer`）

> 骨架照 [`../REVIEW-BEFORE-PUSH.md`](../REVIEW-BEFORE-PUSH.md) §5；只读，不碰 git。
> 范围一变（哪怕只是多传一张图）就作废重审。

```markdown
## 结论：可推送 / 有条件通过 / 阻止

范围：<分支名 / 文件清单>
脚本：`tool/check_upload_safety.ps1 -All` → BLOCK=<n> WARN=<n> INFO=<n>（退出码 <n>，扫描 <n> 个文件）
人工项：图片 <n> 张已看 / <n> 张待 `lead` 人眼确认

### 阻断项（有则必须修完）

1. `<文件>:<行号>` —— 命中什么、为什么是阻断、怎么改

### 条件（有条件通过时列出）

1. `<文件>:<行号>` —— 改法（改成什么、放哪里）

### 逐文件意见

| 文件 | 必要性 | 本机信息 | 硬编码 | 结论 |
|---|---|---|---|---|
| `<路径>:<行号>` | 必需 / 默认排除 / 留档例外（理由） | 无 / 提示 / 警告 / 阻断 + 具体是什么 | 合理 / 建议提取 / 必须外置 | 保留 / 改后保留 / 排除 / 阻断 |

### 已推送内容的遗留问题

- 严重度 / 影响 / 补救成本 / 建议动作（无则写「范围里没有已推送内容」）

### 需要 `lead` 人眼确认

- 图片清单与要看的点（每张：路径 / 用途 / 已确认无个人信息 或 需人眼确认）

### 复核记录

- 改动落地后重跑：`BLOCK=<n> WARN=<n> INFO=<n>`（退出码 <n>）；WARN 逐条结论：<...>
```

**填写要求**

- 「本机信息」列**不许写「无」了事**：要么写明确认无，要么写清命中什么
  （路径 / 设备 / 凭据 / 代理 / 邮箱 / 真实个人数据）。
- 描述本机特征一律用 §9 占位符（`<盘符>` / `<本机用户名>` / `<工程根目录>` /
  `<adb 序列号>` / `<厂商机型号>` / `<本机代理端口>` / `<内网网段>` / `<私人邮箱>` 等），
  报告本身也要入库，不得写入真实值。
- 每条「排除」都要说明是否涉及 git 历史（已推送的才涉及）。
- WARN 没有被逐条给结论时，整份报告视为**未审核**，不能推。

## 4. 三份报告的共同规矩

1. **只写结论，不写过程。** 报告不是工作日志：不写「我先看了 A 又看了 B」，
   只写查到了什么、结论是什么、下一步做什么。
2. **每条都要有可执行动作。** 要么是「改成 X」，要么是「保留，理由是 Y」；
   「建议关注一下」这种没有动作的句子不算一条意见。
3. **结论不许出现「基本没问题」。** 只能用结论词表里的词；
   证据不足就写「证据不足」并点名缺什么证据。
4. **审查者不代改代码、不碰 git。** 报告交回 `lead`；改由实现者做，
   `git add/commit/push` 只有 `lead` 能执行。
5. **点名到行。** 每条意见都要给 `<路径>:<行号>`（信息审核给文件级 `<路径>:<行号>`），
   让人能直接跳过去。
6. **顺序不可颠倒。** 规格符合性（G4）没过，不得启动质量审查（G5）；
   有未修复的阻断项，不得开下一张卡。
7. **写清写作用域。** 报告文件本身落在任务卡声明的 scope 内（审查者默认只写自己的报告文件）。
8. **复核要重跑，不要凭记忆。** 落地后重新执行同一条命令，把计数与退出码再贴一次。
